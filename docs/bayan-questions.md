# Bayān open questions

Questions the spec does not answer yet. Rules (`docs/bayan-contributing.md`, *Ground rules*): a spec gap or contradiction goes here with the next free Q number, in number order; the most conservative option is implemented until the user answers. When a question is answered, move its entry to a dated record in `docs/decisions/` and keep its Q number: other docs cite Q numbers, and they never change. Questions answered up to 2026-11-14 are in `docs/decisions/2026-11-14-004-answered-questions.md`.

In each entry, *Current choice* or *Conservative option* is the option in force, and *Open* or *Options* lists what is still to decide. *Who decides* is the entry's *Owner* where it names one, otherwise the user.

### Q60

60. **Taint sources (spec 002).** *Current choice:* `Untrusted<T>` is a type plus sinks only: `Io.runBatch` and `Io.run` reject it in the program, path or any argument (BYN2786; `Io.run` since 2026-10-21, Q67) and `trust(x, reason:)` unwraps it (BYN2787 for an empty reason). Sources (`args`, `Io.stdin`, file reads, environment) return plain values, not `Untrusted<T>`. *Open:* which sources wrap their results, and which other sinks (SQL, paths) reject it.

### Q64

64. **`take()` (laws revision, 2026-10-20).** *Answered 2026-10-21 (spec 003):* `take()` exists on `List`, `Map`, `StrBuf` and optionals of them (BYN2788 on anything else); an unwritable place gives the existing mutation diagnostic (BYN2104/BYN2106); `map[k].take()` panics on a missing key. A `StrBuf` cannot be a struct field (BYN3001), so `take()` on it is reached only through a local or `ref`. *Open:* `take()` on a `unique struct` whose fields all have empty values.

### Q66

66. **Runtime ownership checker and program generator (L008).** *Answered 2026-10-21 (spec 003):* debug builds (`-DBYN_DEBUG`) keep an owner table keyed by storage address plus a moved slot per owning local; `move`, `take()` and `switch (move x)` transfer ownership, growth sites rekey, and a second owner or a read or move through a moved-from local panics with both locations. Safe and fast C is byte-identical to before (checked over every `run/` golden). `CompilationOptions.SkipOwnershipCheck` is the test-only switch. `OwnershipGenerator` (splitmix64, grammar in its doc comment) feeds `L008OwnershipRuntimeTests`; L008 is enacted. *Open:* the checker does not track storage inside optionals, unions, arrays or collection elements on its own (ASan still catches a use after free there); the panic exit status on Windows is untested.

### Q68

68. **L006's accepted `.copy` clause (review, 2026-10-21).** L006 accepts "the same programs written with an explicit `.copy(to: alloc)`", but only `List`, `Map` and `StrBuf` have `.copy`; a struct, union, tuple or optional holding a unique part does not (`BYN2003: copy is not a member of Ledger`). *Current choice:* the statement stays as the user wrote it; the proof checks `.copy` for the three types that have it, and the proof notes say so. *Open:* narrow the statement to "types that have `.copy`", or give user types a derived `.copy` (spec 003 or later).

### Q69

69. **`move x switch { … }` precedence (spec 003).** *Current choice:* `move` is a prefix operator binding looser than the postfix `switch`, so `move x switch { … }` parses as `move (x switch { … })` and the expression-form owning switch needs `(move x) switch { … }`. The statement form `switch (move x)` has no such issue. *Open:* whether `move x switch` should parse as `(move x) switch`; the self-hosted parser (spec 009) must match whichever is chosen.

### Q70

70. **Mutating an owning binding in a `when` guard (spec 003 review).** In `switch (move s) { case .Full(var x) when x.grow() > 50: … case .Full(var y): … }`, `x` is a copy of the subject's part, so a guard that mutates it and then fails leaves the next arm's binding with the subject's old header; when the guard grew the list past capacity, `main`'s allocator (libc `realloc`) had freed that buffer, and growing `y` was a double free in safe mode. *Current choice (conservative):* inside the guard of an owning switch the arm's bindings are read-only; a mutation, assignment, `ref`/`out` pass or move there is BYN2791. *Open:* allow guard mutations with defined semantics (a failed guard's changes given back to the subject) if a port needs them.

### Q78

78. **Mutating methods and live borrows (spec 004, from T8).** *Decided 2026-10-21:* a call to a mutating method counts as a mutation of the receiver's root local, so it is BYN3004 while any borrow of that root is alive. This closes `lexer.push(t)` while a `tokens()` span is alive, and the same pre-existing gap for `for` loops. Loans stay per root local, not per field path, so `for (t in r.tokens) { r.source.mutate(); }` is a false positive; `selfhost/lexer/dump.byn` avoids it by indexing. *Open:* per-field-path loans, likely needed before the parser port (spec 009).

### Q81

81. **Secondary spans (spec 005).** *Decided 2026-10-21 (spec 005 plan):* `Diagnostic.Related` exists and renders, but no binder site is converted in 005: converting `BYN2104` from label "declared with `let` on line 9" to a secondary span changes its label text and so its JSON. Conversion of the 8 "on line {n}" sites is a follow-up with its own JSON decision. *Answered 2026-10-22:* built as decided; `Related` renders (golden `diag-secondary`) and no binder site uses it. The follow-up stays open.

### Q114

114. **`asSpan()` on a `let` List (found in the 006 review, 2026-10-23).** *Open:* `asSpan()` returns a writable `Span<T>` whatever the receiver, so `let k = List<i64>(); k.asSpan()[0] = 5;` compiles and a `let` List can be changed through a span. The spec (§ conversions table, rule on spans) does not say. Conservative option: on a non-writable place `asSpan()` returns `ReadOnlySpan<T>`. Not implemented; waiting for the user.

### Q160

160. **Round 3 step 5.1e: `extern` is still BYN1016.** BYN1067 allows pointer types only in `extern` declarations, but the `extern` modifier is still rejected (BYN1016), so no pointer is legal anywhere and `bayan format` cannot apply BYN1066's fix (BYN1067 blocks the file). *Current choice (conservative):* `extern` stays rejected, since no step row makes it parse; the parser tracks `extern` so BYN1067 is skipped inside one once it is allowed. Which step accepts `extern` declarations?

### Q342

342. **Review round 3 (A1): a generic that replaces a `ref T` instantiated with a type that has states.** `void put<T>(move T v, to ref T x) { x = move v }` is fine on its template, but with `T = Order` (a struct with states) the assignment changes `x`'s state, which revision 0010 rule C forbids; the instance's BYN7012 used to stop the compiler with an internal error. *Current choice (conservative: reject):* BYN7012 is reported at the call that chose the type arguments (label "the generic code needs this of its type arguments"), with a related span labelled "in `put`" at the assignment when it is in the same file and help naming the generic. A call that would keep the state (the value given is in the place's known state) is still rejected, since the template cannot see states. *Open:* accept such instantiations when the argument is provably in the same state, or a constraint that excludes types with states.

### Q344

344. **Re-review rr6: `==` on an error set whose case holds a payload with no equality.** `union error ListError { bad(List<i64> items) }` has a case that cannot be compared, so comparing two `ListError` values cannot compare their payloads. *Current choice (conservative: reject):* `==` and `!=` on such a set (or an error union or `Result<T, E>` that includes it) is BYN2208, the diagnostic for any type without equality; `==` against a bare case (`l == .bad`) still compares the code (Question 312). Other sets compare as before; the C helper leaves such cases out. Open: compare the code only, or compare the comparable cases.

### Q364

364. **007 T4: named functions as values, corners R3/R4 leave open.** (a) A function declared `fails` without a list has its sets inferred after binding, so at the conversion they are unknown. *Current choice (conservative: reject):* it is not a value of any function type (BYN2202, its signature shown with a bare `fails`); declare the sets to pass it. (b) A function with a `ref`, `out`, `move` or `in` parameter, or whose `fails` clause takes cases out (`except .c`), has no function type to match; BYN2202. (c) Of overloads (J65) the first whose signature matches the type is the value. (d) BYN2824's "constructor" covers a struct `S(…)` builds (a constructor, a distinct type, `@positional`); any other struct named as a value stays BYN2019. (e) The BYN2824 help's lambda takes as many parameters as the function type passes, named after the callee's, so a built-in's defaulted tail is left out (`text => print(text)`). New.

### Q365

365. **007 T5: lambda names in BYN6005 and the typed dump.** A lambda is lifted as `<enclosing>$lambda<N>` (numbered per enclosing function in binding order), and BYN6005 on a lambda stored in a function-typed local names it that way ("`stored$lambda1` uses `console`, beyond the bound `pure` declared by `i64 -> void`"). *Current choice (conservative: keep):* the lifted name is shown as is, since it is also the name in `bayan types`; a message that says "this lambda" instead would need a second message form. New.

### Q366

366. **007 T5: typed-dump version for `captures`.** Lambdas in `functions[]` gain a `captures` array (`name`, `type`, in first-use order); other functions do not have the field. *Current choice (conservative: keep version 1):* the field is additive and only appears on lambdas, which no earlier dump contained, so no existing reader sees a change. New.

### Q367

367. **007 T6: where a lambda value's lifetime ends, and the done-when items the earlier tasks already settled.** (a) A lambda with captures borrows its environment, which lives in the creating frame and is reused by each iteration of the loop that creates it (plan risk *Environment temp per evaluation*, Q345); the captures' own borrows alone cannot catch a lambda capturing only `i` held into the next iteration, or a lambda returned from a lambda. *Current choice (conservative):* `RegionAnalysis` gives a capturing lambda a region named "the lambda on line N" at the innermost loop's iteration depth, or the function body outside a loop, so it may be held by any local in its iteration or frame (also from an inner block, as a borrow-free local) but kept into the next iteration is BYN3002 and returned (a lambda returning a capturing lambda) is BYN3003; a non-capturing lambda borrows nothing. (b) The T6 line asks for BYN3004 when the buffer a captured `string` borrows is *appended* to; `append` is not a structural change (Q30, Q43: a grown `StrBuf` leaves earlier text valid), so for any borrow, lambda or not, it is accepted; the golden appends (accepted) and then `clear()`s (BYN3004 naming the buffer). (c) A function value stored in a struct field (BYN3001) or returned from a named function (BYN3003) cannot be written: the field or return type is already BYN2822 (Q346, `function-type-placement`), so BYN3003 is shown for a lambda returning a lambda and BYN3001 has no golden. (d) A captured `unique` value's BYN2780 help offers only copying what the lambda needs into `let` values, with no fix: `move` and `.copy(to:)` would leave a unique local that is captured the same way. New.

### Q370

370. **007 T11: L014's "nested `let` shadow" scenario cannot be written.** Spec 007 L014 and the T11 line ask that an accepted capture still print its creation value after "a later `let` shadow in a nested scope", but a `let` in a nested scope that hides an outer local is BYN2007 (Bayan does not let a local hide another one), so no accepted program has that shape. *Current choice (conservative: keep BYN2007, test the nearest legal shapes):* `tests/cases/run/lambda-capture-by-copy.byn` redeclares the captured name in the same scope after the lambda is created, with another type (the same type is warning BYN2028), and declares the name again in a sibling nested block after the source's scope has ended; `L014CaptureByCopyTests` checks both. The designer should either reword L014 to these shapes or say whether nested shadowing should become legal. New.

### Q371

371. **`HashMap` or `Map` (spec 008).** 008 extends `Map` (new key types, `Symbol`) and does not add `HashMap`. *Current choice (conservative):* `HashMap<K, V>` is BYN2830 with a fix to `Map<K, V>`, wherever a type is written, and then resolves as `Map<K, V>` so it is reported once; `bayan format` does not apply the fix (a checker diagnostic). One map with deterministic iteration serves self-hosting (stage 2 and 3 byte-identical, L009); an unordered `HashMap` can be added later without breaking any program, while removing one could not. *Open:* whether v0.1 or a later version adds an unordered `HashMap` (SPEC §3.5 had one).

### Q415

415. **008 T10: the padding case of L016 cannot be made to fail on this toolchain.** T10's done-when asks that a mutation back to `byn_hash_bytes(&k, sizeof k)` make the padding case fail. On zig cc and Apple clang (macOS arm64), no Bayan program I could write gives two `==` keys different padding bytes, in debug or safe mode. The reasons: compound literals zero their padding, small fields are masked in registers, every local starts as `= {0}`, and struct copies move every byte. Stack smearing, separate frames, field-by-field writes, `i8` narrowed from wide registers, list and map storage and `-ftrivial-auto-var-init=pattern` all keep the padding equal. *Current choice (conservative):* L016 keeps the padding rows (`PaddedKeysBuiltApartAreOneEntry`) as a guard for other compilers, and the mutation is killed through `string` parts (raw bytes hash the pointer). The proof notes say the padding half holds by construction, not by a failing mutation.

### Q1007

1007. **012 T15: `Target.os`/`Target.arch` are not constant expressions without `--target`, and the `#else ""` arm is untestable (round 2, LOW 2/4).** `const os = Target.os` fails with BYN2219 when there is no `--target`: `BoundHostTarget` has no `Constant` (BinderExpressions.cs:717), unlike the literal a given `--target` binds (BinderExpressions.cs:719-720), so the same program compiles or not depending on the flag. *Current choice (conservative, Q975):* keep it; Q975 makes the value a preprocessor constant, which the binder cannot fold. The alternative is to reject `Target.os` in constant position with a dedicated diagnostic, or to fold it for the host. The `#else BYN_STR("", 0)` arms of `BYN_HOST_OS`/`BYN_HOST_ARCH` in `bayan-rt.h` (Q973) cannot be reached on the supported hosts (macOS, Linux, Windows; x64, arm64), so no test covers them. Open.

### Q1084

1084. **017 T3: `clean` on Windows still follows a directory symlink.** `t3RemoveEntry` (cache.byn:87 `Io.remove(path) catch return false`, in `t3Unlinked`) relies on POSIX `unlink` removing a symlink to a directory. On Windows `DeleteFileW` does not remove a directory symlink, so `Io.remove` fails, `t3DirectoryExists` holds, and the self-hosted driver recurses into the target and deletes its contents, where the C# `Directory.Delete(recursive: true)` removes only the link. A fix needs an `Io` link query (an A1 exception, plan D7). Meanwhile the POSIX fix only; not run on Windows. Open.

The C# filter `f.File is not null && f.Location is not null` is `file >= 0` (a Bayan symbol with a file always has a span), and the local filter `l.Location is not null` is dropped, because every Bayan local has a `span` (a `TextSpan`, never absent), and the dump writes that field (typed.byn:45). `t26JsonString` escapes `"`, `\`, the short forms `\b \t \n \f \r`, `\u00XX` (upper-case hex) for the other C0 controls, DEL and C1, `\u2028`/`\u2029`, and a code point above U+FFFF as its surrogate pair. Everything else is copied, as an fsi probe of the encoder showed. `JsonStringsMatchUtf8JsonWriter` compares those classes against `Utf8JsonWriter`. Other format, unassigned or private-use code points are not compared, so whether the encoder escapes any of them is open. With each typed case copied alone into a directory, 17 of 18 match `bayan types` byte for byte; the 18th is in Q649.
