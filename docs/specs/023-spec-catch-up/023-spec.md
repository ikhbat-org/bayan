# 023 — Spec catch-up: build what the spec describes
Status: draft
Release: unscheduled
Sources: docs/bayan-spec.md; docs/STATUS.md; docs/bayan-roadmap.md; user 2026-11-16 (order 019 → catch-up → 020; a reviewable catch-up spec)
Created: 2026-11-16

## Problem
`docs/bayan-spec.md` and `docs/STATUS.md` list many language, library and tooling features as `spec-only`, `partial` or `deferred` (`(not in 0.3)`, `(partial in 0.3: …)`, `(not in 0.x)`). Until now, every compiler change had to land in two implementations and pass parity harnesses across both. On 2026-11-16 the user fixed the execution order:
1. **Spec 019** (the .NET exit: retire the old compiler and xUnit test suite, move `bayan-lsp` and goldens to Bayān, build from the C bootstrap, and keep the old compiler frozen for diverse double-compiling).
2. **Spec 023** (this catch-up: build the unimplemented spec features in the self-hosted compiler only).
3. **Spec 020** (test-result cache, `docs/specs/020-test-result-cache/020-spec.md`).

Without a single verified inventory, a 0.4 cut line, a verification method per item once the second compiler is frozen, and a dependency order that brings in test tooling early and unblocks spec 015 (`T14`–`T17`), catch-up work after spec 019 risks building underspecified features (`comptime`, `scope`/`spawn`) before foundational types and checks, or losing verification coverage once the old oracle stops growing.

## Goals
- Verify every `spec-only`, `partial` and `deferred` feature across `docs/STATUS.md` and `docs/bayan-spec.md`, citing its section, current state, dependencies, size estimate (`S` under 3 days, `M` about 1 week, `L` 2 to 3 weeks, `XL` more), spec readiness, 0.4 cut status (`needed for 0.4` vs `may stay spec-only after 0.4`), and how its goldens are checked without a second active compiler.
- Sequence the catch-up into dependency-ordered phases with a testable done-when criterion per phase, built exclusively in the self-hosted compiler and standard library after spec 019 lands.
- Move test tooling (`provide` handlers, `Io.Simulated`, `property` tests from `requires`, `fuzz`) as early as its dependencies allow so it replaces part of the confidence the retired oracle gave, while keeping strict dependency order (`requires` before `property` generation, `provide` handlers before `Io.Simulated`, `@derive` before derived law tests).
- Name and schedule the exact blockers into spec 015 (`std.regex` blocking 015 `T15`, `Io.run` streaming blocking 015 `T17`).
- Isolate every spec gap into an explicit open question with a conservative default so phases with complete spec text can proceed without blocking on thin sections.

## Non-goals
- Implementing any catch-up feature before spec 019 completes, or porting any new feature to the frozen compiler.
- Breaking the revision 0023 syntax freeze before the `v0.3.0` release tag exists, except revision 0024 (numeric conversions).
- Designing or implementing items outside `docs/bayan-spec.md` (such as `.par()`, `bayan verify`, Sabk native backend, `kit.*` packages or post-v1 targets in Appendix B).
- Building spec 020 (test-result cache), which follows the 0.4 catch-up cut.

## Requirements
- **R1 Self-hosted only, after 019.** Every item in this spec is implemented in the self-hosted compiler, runtime and standard library after spec 019 retires the old compiler and test host. Every new diagnostic has a diagnostic golden case and an explain page; every runtime or library feature has a run golden case or standard-library test.
- **R2 Freeze compliance.** Under `docs/revisions/0023-syntax-freeze-provisional-sections.md`, no revision adds, removes or renames a keyword, operator, clause or grammar form until the `v0.3.0` release tag exists; revision 0024 (numeric conversions) is the last syntax change admitted during the freeze. Since spec 019 and this catch-up run after the `v0.3.0` tag, post-0.3.0 syntax items may land once their spec text is settled.
- **R3 Inventory completeness.** The inventory table below covers every feature marked `spec-only`, `partial` or `deferred` in `docs/STATUS.md` and `docs/bayan-spec.md`, plus the `Io.run` streaming blocker for spec 015 `T17`. Features already `built` in `docs/STATUS.md` (`Untrusted<T>`, `because`, particles, `rest`, `expects`, typestate `states`/`becomes`/`become`, `when` guards, `do` loops, `new` removal, `f64.tryParse`, `Display.formatInto`, `as: .debug`, style layout and lints BYN1072 to BYN1080, and naming lints BYN5101 to BYN5107) are excluded.
- **R4 Cut line for 0.4.** Each inventory item and each phase is marked either `needed for 0.4` or `may stay spec-only after 0.4 (keeps its STATUS tag)`. Phases 1 through 4 form the `0.4` cut; Phases 5 and 6 may stay `spec-only` after `0.4` and keep their provisional tags in `docs/bayan-spec.md` and `docs/STATUS.md`.
- **R5 Verification without a second compiler.** Because spec 019 freezes the old C# compiler at the 0.3.0 language surface, every inventory item states how its goldens and behavior are verified: (a) the frozen C# binary where the feature uses only 0.3 syntax/runtime or has a reference helper, (b) a second mechanical method (`property` tests, `fuzz`, differential testing against a reference implementation or `bayan expand` round-trip), and (c) human review of diagnostic and run goldens.
- **R6 Phase gates.** Work proceeds in Phases 1 through 6 below. A phase starts only when its dependencies are met and any blocking open question for an item in that phase is settled (or its conservative option is enacted by revision).
- **R7 Status synchronization.** Each commit that lands a catch-up item updates its row in `docs/STATUS.md` (with golden evidence), removes the corresponding `(not in 0.3)` or `(partial in 0.3)` tag in `docs/bayan-spec.md`, and regenerates the keyword and stdlib tables. Items marked `may stay spec-only after 0.4` keep their tags until built.

- **R8 `checked` warns when it covers nothing.** A `checked(...)` holding no covered operator gets a warning. Covered operators are those of OQ2, on `dec` as well (OQ2).
- **R9 `Secret<T>` owns its bytes.** `Secret<T>` keeps a heap copy of its bytes and wipes it on dispose. §15.2 says the owned buffer is wiped and does not promise that no trace remains in registers or spilled stack (OQ3).
- **R10 `embed` has one rule set.** One `embed` per struct; every name collision with the outer struct is a compile error in 0.4. The revision gives a way to name the embedded value as a whole (OQ5).
- **R11 `fuzz` runs in a child process.** Each input is saved before it runs, so a trap is reported with its input (OQ11).
- **R12 Built-in derives generate Bayān source.** Built-in derives produce Bayān source or AST, not C emitted by special cases, so `bayan expand` prints what was compiled (OQ13).
- **R13 Concurrency is built in stages.** `Io.Blocking` runs `spawn` children inline first, then one worker, then per-core. No parallel thread pool comes first (OQ15).
- **R14 The process API is a handle.** `Io.run` streaming is a process handle whose reads use the `read(into:)` shape and return the next chunk from stdout or stderr, whichever is ready (OQ17).

### The 0.4 cut line and why

After spec 019 retires the old compiler, the project needs: (1) the remaining spec 015 tooling ports (`T9`–`T17`) so Python scripts leave CI, (2) self-hosted test tooling (`provide` handlers, `Io.Simulated`, `property` tests, `fuzz`) to replace the differential confidence the second compiler used to provide, and (3) the core type, pattern, closure, collection, unit, `std.time`, FFI and built-in `@derive` features that Sūq and standard library code use directly. Those make up **Phases 1–4 (`needed for 0.4`)**, after which spec 020 (test-result cache) can run on a stable test runner.

Items that require external infrastructure (`package.lock.byn` registry protocol, `std.db` schema snapshots), unbuilt secondary tools (`bayan-prose`, `bayan repl`), or major new execution models whose spec text is thin or a placeholder (`comptime` interpreter, `scope`/`spawn` fibers, `model test` / `xOp`, `yield` state machines, `actor`/`macro`/`select`) are marked **`may stay spec-only after 0.4 (keeps its STATUS tag)`** in **Phases 5–6**. Revision 0023's provisional-text rule allows them to keep their tags in `docs/bayan-spec.md` and `docs/STATUS.md` at zero compatibility cost until their design revisions are settled.

### Blockers into spec 015 (tooling ports)

Spec 015 (`docs/specs/015-tooling/015-tasks.md`) has nine open tasks (`T9`–`T17`). Two depend on catch-up items in Phase 1 of this spec:
- **`std.regex` (item #18) blocks spec 015 `T14` and `T15`:** `T14` builds the `std.regex` module, and `T15` ports the `guard-checks`, `coverage-gate` and `wave-brief` tools from Python onto `std.regex`.
- **`Base64` in `std.encoding` (item #18) is spec 015 `T16`:** `T16` adds `Base64.encode` and `Base64.decode`.
- **`Io.run` process-handle / byte-exact streaming (item #25, Q1141) blocks spec 015 `T17`:** `T17` ports the `replay` tool to Bayān, which is gated on Q1141 (a streaming or byte-exact process API so `replay` can replay arbitrary child stdout/stderr bytes without UTF-8 loss or 4.6 GB unbounded buffering, Q1227).

### Proposed order in phases

The six phases order items by: (1) unblocking spec 015 tooling ports (`T14`–`T17`) immediately in Phase 1, (2) moving self-hosted test tooling (`provide` handlers, `Io.Simulated`, `property` tests, `fuzz`) into Phase 2 as early as its dependencies allow so that every later phase is verified by property and fuzz tests now that the C# oracle is frozen, (3) respecting compiler and stdlib dependencies (`requires` before `property` generation; `provide` handlers before `Io.Simulated`; units and unions before `std.time`; closures before `Event<T>` and lazy collections; `@derive` before derived law tests), and (4) placing thin or placeholder items after the `0.4` cut line in Phases 5 and 6.

#### Phase 1: Numerics, contract hardening, and spec 015 tooling blockers (`needed for 0.4`)
- **Items:** #1 (rev 0024 numeric conversions and `dec`), #2 (`small` build mode, `checked(expr)` and `if unlikely` hint emission), #3 (`BYN6008` contract purity and `requires` on aliases/generics), #18 (`std.regex`, `Base64`, `std.text` members, and `grouping:`/`case:` format specs), #25 (`Io.run` streaming / byte-exact process API, Q1141).
- **Why first:** Revision 0024 is the last syntax change from the 0.3.0 freeze; `#3` completes `requires` so Phase 2 can generate `property` inputs from `requires` rules; `#18` (`std.regex` and `Base64`) and `#25` (`Io.run` streaming) unblock spec 015 `T14`, `T15`, `T16` and `T17`, letting the repository finish retiring Python tooling right after spec 019.
- **Done when:** Revision 0024 is applied; `dec`, `--mode small`, `checked(expr)`, `if unlikely`, `BYN6008`, `std.regex`, `Base64`, `std.text`, `grouping:` and `Io.run` streaming pass their run and diagnostic goldens; and spec 015 `T14`–`T17` are unblocked.

#### Phase 2: Early test tooling (`provide`, `Io.Simulated`, `property`, `fuzz`), type-system completions, units, and patterns (`needed for 0.4`)
- **Items:** #16a (`provide` handlers beyond `alloc`, `log` handler, `context` values, `effect` aliases, `Io.Simulated`), #19a (`property` tests driven by `requires`, `fuzz`, `@cases(constList)`, `@pairwise`, `bench`, doctests), #4 (`Secret<T>`, `@secret`, trust sinks), #5 (`except` sequence form), #6 (`open` and `extensible` enums/error sets), #7 (`embed`), #8 (`attribute` declarations and `@json`/`@column`), #9 (`unit` declarations and suffixes), #10 (optional chaining `?.`, named patterns, full pattern forms, operator overloading), #11 (union/enum members, `tryParse`, interface conformance), #12 (`extension`, `static abstract`, generic methods on types/interfaces, `const` type parameters, type overloads).
- **Why second:** After spec 019 freezes the C# compiler, new features have no second compiler oracle. Building `#16a` (`provide` handlers and `Io.Simulated`) and `#19a` (`property` and `fuzz` testing, which depend only on Phase 1's `#3` `requires` rules and `#16a`) at the start of Phase 2 gives Phases 2–6 a mechanical second verification method (property-based laws and fuzzing). The remaining items (`#4`–`#12`) complete the type, unit, pattern and generic system needed by `std.time`, `Event<T>` and collections.
- **Done when:** `provide` handlers, `Io.Simulated`, `property` tests, `fuzz`, `bench`, doctests and items `#4`–`#12` pass `bayan test`, and every new feature in Phase 2 is covered by a `property` or `fuzz` test in addition to reviewed goldens.

#### Phase 3: Closures, events, collections, `const Symbol[N]`, and `std.time` (`needed for 0.4`)
- **Items:** #13 (first-class closures, `dyn (A -> B)`, `ref` and `move` captures), #14 (`Event<T>`, `Subscription`, `raise`), #15a (`Set<T>`, `Deque<T>`, `Pool<T>`, `Ring<T, const i32 N>`, typed indices `List<T, I>`, `const` `Symbol` arrays, lazy collection queries `where`/`select`/`sumBy`/`sort(by:)` and lazy readers), #16b (`std.time` module and date format specs `as: .iso / .date / .time`).
- **Why third:** Closures (#13) unlock `Event<T>` (#14) and lazy collection methods (#15a); units (#9), union members (#11) and `provide clock` (#16a) from Phase 2 unlock `std.time` (#16b).
- **Done when:** Stored closures, `Event<T>`, collection queries, `Set<T>`, `Deque<T>`, `const` `Symbol` arrays and `std.time` pass `bayan test` (including `@timeSensitive` and `property` suites) with zero leaks under the release memory gate.

#### Phase 4: C FFI, built-in `@derive`, derived `format()` / Debug `dbg(x)`, `-er` doer pattern, `bayan expand`, and derived law tests (`needed for 0.4` — 0.4 cut line)
- **Items:** #17 (`extern c`, `unsafe because`, `cstr`, `T*`, `@link`, `@cLayout`, `@exportC`), #20a (compiler-built `@derive(Display, Order, Id, Builder, Patch, Field, Json, Csv, Row, CopyIn)`, derived allocating `format()` and `dbg(x)`, `-er` doer pattern and noun patterns `T.Builder`/`T.Patch`/`T.Field`/`T.Id`, verb derivations `tryX` and `xInto` → `x()`, `T.rules`, and `bayan expand`), #19b Part 1 (automatic derived law tests and `law` execution, which depend on `#19a` `property` tests and `#20a` `@derive`).
- **Why fourth:** FFI (#17) builds on `open` enums (#6); building the standard `@derive` targets, noun/doer patterns and verb derivations directly in the compiler (#20a) unlocks automatic derived law tests (#19b Part 1) and `bayan expand` without waiting on the full `comptime` interpreter. Completing Phase 4 reaches the **0.4 cut line**, after which spec 020 (test-result cache) runs.
- **Done when:** A Bayān package links and calls a C library through `extern c` and `unsafe because`; `bayan expand` prints derived members and effects that splice back cleanly; `@derive(Json, Builder, Patch, Field, Row)` and automatic derived law tests pass in `bayan test`.

#### Phase 5: Lockfile, packages, `std.db`, `yield`, proof-based check removal, and secondary CLI tools (`may stay spec-only after 0.4 (keeps its STATUS tag)`)
- **Items:** #3 Part 2 (proof-based check removal for `expects`, bounds and overflow), #15b (`yield` generator iterators), #22 (`package.lock.byn`, `bayan pkg add/audit/export/diff`, `build.byn` sandbox), #24 (`std.db`, `bayan migrate`, `bayan new test`, `bayan doc`, `bayan repl`, `bayan-prose`, script directives).
- **Why fifth (post-0.4 cut):** `std.db` depends on C FFI (#17), `@derive(Row)` (#20a) and `effect` aliases (#16a); package tooling (#22) requires OQ14 (lockfile schema and registry hosting) settled; `yield` (#15b) requires OQ8; proof-based check removal (#3 Part 2) is an optimization over checks that already run in every build mode. None blocks single-package self-hosted development or Sūq core logic.
- **Done when:** `bayan build` writes and verifies `package.lock.byn` with SHA-256 hashes, `bayan pkg export --json` and `bayan pkg diff` pass golden tests, `yield` generators match hand-written iterators, and `std.db` runs parameterized `sql"…"` queries against a C database driver.

#### Phase 6: Comptime, user derivations, `model test`, and structured concurrency (`may stay spec-only after 0.4 (keeps its STATUS tag)`)
- **Items:** #21 (`comptime` interpreter, `typeof(T)` / `TypeInfo`, `Program` queries, `diagnostic` declarations), #20b (user-written `derivation Name for T` and `xOp` / `Op<T, E>`), #19b Part 2 (`model test` using `xOp`), #23 (`scope` and `spawn` concurrency, `ISendable`/`IShareable`, fibers, `Io.Evented`, and multi-threaded/multi-table `Symbol.intern` from #15a; `actor`, `macro` and `select` remain reserved keywords).
- **Why last (post-0.4 cut):** These items have thin or placeholder spec text today (§12 leaves `TypeInfo` and reflection AST shapes underspecified; `Op<T, E>` is undefined in §5.2; §13 is a placeholder pointing to `docs/bayan-concurrency.md`) and carry the highest implementation risk (`XL`).
- **Done when:** Spec revisions for §12, `Op<T, E>` and §13 are approved; the deterministic `comptime` interpreter enforces the 10,000,000-step and 256 MiB budgets and runs user-written `derivation` declarations; `model test` runs stateful operation sequences; and `scope`/`spawn` pass concurrency, cancellation and `ISendable` goldens.

## Law candidates
- **Unit erasure and dimensional safety:** for every expression over unit types that passes `bayan check`, the emitted C is identical to the underlying integer arithmetic with explicit scale factors, and no bare numeric literal (`0` included) is accepted where a unit type is expected.
- **Derivation equivalence:** for every type `T` and standard derivation `D`, compiling `T` with `@derive(D)` produces the same diagnostics, effects and runtime behavior as compiling `T` with the output of `bayan expand T` spliced into the source (§12.5).
- **Comptime determinism:** for every `comptime` evaluation, running it on any host architecture or OS with the same inputs produces identical `.rodata` bytes or fails at the exact same step count under the 10,000,000-step budget (§12.2, §12.3).
- **Scope lifetime containment:** for every `scope` block, no spawned child fiber is running after the `scope` block exits (whether by normal completion, `fail`, cancellation or timeout), and no borrow into the parent frame outlives the `scope` (§9.4, `docs/bayan-concurrency.md` §3).

## Open questions
Each open question names a place where `docs/bayan-spec.md` is not concrete enough to build from today, together with the conservative option that holds until the user decides:

- **OQ1 (`dec` representation and rounding, §3.1, §6.2, rev 0024):** §3.1 names `dec` and `1.50dec`, and Q1274 settles `dec(0.1)` and `dec(f64)`, but the bit width, scale range and division rounding mode of `dec` are not in the spec. *Conservative option:* 128-bit fixed-scale decimal (96-bit signed integer coefficient, scale 0..28, banker's rounding to nearest-even on division, trapping on overflow).
  *Resolved:* closed by revision 0024, which has status done (text written 2026-11-17). `dec` is built from §3.1 and `docs/bayan-spec.md` as written: a 96-bit unsigned coefficient plus a sign bit, scale 0..=28, one rounding to nearest with ties to even, trapping on overflow and division by zero. The 'signed coefficient' wording above is out of date (owner, 2026-11-17, Fable's recommendation).
- **OQ2 (`checked(expr)` scope, §6.2):** §6.2 says `checked(expr)` evaluates a whole expression with overflow detection and returns `T?`, without stating whether calls to user functions inside `expr` are also converted from trapping to `null` or only arithmetic and narrowing operators written in `expr`. *Conservative option:* `checked(expr)` covers `+`, `-`, `*`, `/`, `%`, unary `-` and narrowing conversions `T(x)` syntactically inside `expr`; calls inside `expr` keep their own semantics.
  *Resolved:* `checked(expr)` covers only the operators and narrowing conversions written inside the parentheses; calls keep their own behaviour, and division by zero still traps. The same operators on `dec` are covered. A `checked(...)` that holds no covered operator gets a warning (R8) (owner, 2026-11-17, Fable's recommendation).
- **OQ3 (`Secret<T>` zeroing and Layer 1/2 sinks, §15.1, §15.2):** §15.2 says `Secret<T>` is zeroed on dispose, and §15.1 lists sink types (`Sql`, `Html`, `PathSegment`, `Url`, `HeaderValue`, `Arg`), which are not all in `core`. *Conservative option:* `Secret<T>` allows `T` to be `string` or fixed-size byte/integer arrays, zeroes heap or inline bytes via a volatile wipe on `dispose`, and restricts `Untrusted<T>` sink checks in `core` to `Io.run`/`Io.runBatch` (already built), `PathSegment` and `Regex.parse` until `std.db` and web packages declare their sink types.
  *Resolved:* `T` is restricted as proposed, but `Secret<T>` always owns a heap copy of its bytes, so a move copies a pointer and leaves no stale bytes. The documented promise is that the owned buffer is wiped (R9). Sinks are added one module at a time; today the list is `Io.run` and `Io.runBatch` (owner, 2026-11-17, Fable's recommendation).
- **OQ4 (Standalone `xs except p` type, §6.8):** §6.8 shows both `for line in lines except inactive` and `let present = users except null`. Outside a `for` head, the concrete return type of `xs except p` is not named. *Conservative option:* `xs except p` returns a lazy filter iterator value (requiring `List(users except null)` or `.copy()` to materialize a `List<T>`), matching `where` in §16.
  *Resolved:* `xs except p` outside a `for` head is a lazy filter value that borrows `xs`, like `where`; `List(seq)` materialises it. The `for` form can land in Phase 2; the standalone form waits for lazy iterators (#15a) and keeps BYN2022 until then (owner, 2026-11-17, Fable's recommendation).
- **OQ5 (`embed` member conflict resolution, §3.10):** §3.10 says `embed T` promotes the embedded struct's fields and methods and sits at offset 0, but multiple `embed` declarations cannot all sit at offset 0 and conflicting member names are unspecified. *Conservative option:* at most one `embed T` per struct (at offset 0); an outer member shadows an embedded member of the same name, and any other collision is a compile error.
  *Resolved:* one `embed` per struct, and every name collision with the outer struct is a compile error in 0.4 (not shadowing; it can be relaxed to outer-wins later without breaking code). The revision also adds a way to name the embedded value as a whole (R10) (owner, 2026-11-17, Fable's recommendation).
- **OQ6 (Compound unit algebra, §3.4):** §3.4 shows `unit Speed = Meters / Seconds`, which requires tracking rational exponent vectors over base units across `*` and `/`. *Conservative option:* build base units (`unit Seconds(s): i64`) and scale-factor derived units (`unit Millis(ms) = Seconds / 1000`, `unit KiB = 1024 B`) first, as needed by `std.time` (§16.5); reject `UnitA / UnitB` and `UnitA * UnitB` declarations with `BYN2022` until a unit-algebra revision specifies simplification.
  *Resolved:* base and scaled units only; `UnitA / UnitB` and `UnitA * UnitB` declarations give BYN2022. The revision states two operator rules: scalar times unit gives the unit, and dividing two values of the same unit gives a plain number (owner, 2026-11-17, Fable's recommendation).
- **OQ7 (Active and positional patterns, §6.5):** §6.5 shows `input is Email(var e)` ("active pattern from `Email.tryParse`") and positional patterns without specifying how positional fields are ordered on a plain struct. *Conservative option:* `T(var x)` in a pattern is allowed on a `type distinct` or a struct with a static `tryParse` or `tryFrom` single-argument member; positional deconstruction on a struct is allowed only when the struct is marked `@positional` (§4.4).
  *Resolved:* `@positional` types read `T(...)` as deconstruction. For any other type, `T(var x)` calls `T.tryParse` (text subject) or `T.tryFrom` (other subject) and binds a `T`. The reading where `type distinct` unwraps is dropped. A struct that is not `@positional` is an error under `T(var a, var b)`. The effects of `tryParse` count at the pattern site (owner, 2026-11-17, Fable's recommendation).
- **OQ8 (`yield` signature and borrow rules, §2.4, §7.4):** `yield` is in the §2.4 keyword table, but §7.4 does not state the return type written on a generator function or whether borrows may cross a `yield`. *Conservative option:* keep `yield` in Phase 5 (post-0.4) until a revision specifies its return type syntax and region rules; hand-written `moveNext(ref this)` / `current` structs (already built) serve in the meantime.
  *Resolved:* `yield` stays unbuilt until a revision defines the return type and the borrow rule, shared with the §13 borrow rule for suspend points (owner, 2026-11-17, Fable's recommendation).
- **OQ9 (`provide` handler types beyond `alloc`, §7.7, §14):** §7.7 shows `provide net: net, clock: FakeClock(…), log: logs`, but §14 does not give the interface or struct signatures that `net`, `fs`, `clock`, `random`, `env`, `process`, `console` and `log` handlers must satisfy. *Conservative option:* specify and build `clock` (`IClock`), `random` (`IRandom`), `console` (`IoStream`), `log` (`ILogSink`) and `Io.Simulated` first in Phase 2 via a small spec revision; keep `net`, `fs`, `env` and `process` custom handlers rejected until their `std` modules land.
  *Resolved:* build `clock`, `random`, `console`, `log` and `Io.Simulated` first. Also include the built-in `fs.restricted` handler (decision 007 Q3); user-written `fs`, `net`, `env` and `process` handlers stay rejected. The fake clock is named `FakeClock`, as the normative spec has it. The interface names `IClock`, `IRandom` and `ILogSink` are proposals, not existing names (owner, 2026-11-17, Fable's recommendation).
