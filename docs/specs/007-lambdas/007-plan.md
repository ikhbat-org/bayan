## Approach

**A function type is a structural `ConstructedType`; a function value is a (code, environment) pair that borrows the frame that made it.** `FunctionType(Parameters, Return, Fails, Uses)` sits beside `OptionalType`, `SpanType`, `TupleType` and the rest in `Types.cs` (built in T2: structural `Equals`/`GetHashCode` over all four parts), with `IsBorrow => true`. That one bit buys R10 for free: region analysis already forbids storing a borrow in a field (BYN3001), returning it (BYN3003) or outliving its source (BYN3002), and reports modification while borrowed (BYN3004). In C the value is `struct { R (*fn)(void* env, A, B[, R* out]); void* env; }`, emitted through `Named`/`EmitTypes` like a tuple; a call through it is `f.fn(f.env, …)`.

**Lambdas are lifted to ordinary `FunctionSymbol`s at bind time; captures are tuple fields.** A lambda binds to a synthesized `FunctionSymbol { Kind: FunctionKind.Lambda, Module, File, Parameters from the expected type, ReturnType, ErrorSets, Fails }` appended to `ModuleSymbol.AllFunctions`, so lowering, the analyses loop in `Compilation.cs`, `bayan types` (`TypedDump.cs`) and emission see it with no new loop. The body is bound inline by the enclosing binder with `_fn` switched to the lambda symbol and a nested scope, so `return` targets the lambda and outer names resolve through `_scope.Lookup` in `BindName`; a resolved outer local is recorded as a capture. The bound expression `BoundLambda(Syntax, Lambda, Captures: BoundLocal[], FunctionType)` lists one `BoundLocal` read per capture as its children (`BoundTree.Children`, built in T2), so flow analysis sees a read, ownership analysis sees a copy (BYN2780 for `unique`) and region analysis sees a value derived from every capture's root, with no lambda-specific rule in any of the three. Lowering spills the captures into a temp of type `TupleType(captures)` (`Lowerer.NewTemp`) and builds the pair from the lifted function's name and `&temp`; inside the lifted function the emitter maps each captured `LocalSymbol` to `((tuple*)env)->itemN` through the function emitter's `_names` map, so the body reads captures as if they were locals. Tuples already have C definitions, keys and equality, so no new type emission is needed for environments. The temp lives for the whole enclosing frame (locals are declared at function top), which is longer than any borrow of the lambda can be (R10). Rationale over monomorphizing the callee per lambda (spec §3.16's "inlined"): one calling convention serves named functions, non-capturing and capturing lambdas alike, the generics machinery is untouched, and inlining stays a later optimisation that changes no observable behaviour (L013 pins that).

**Named functions as values reuse the `BoundMethodGroup` hook.** `BindOnPanic` (`Binder.cs`) already recognises a module function named as a value and renders its signature for a mismatch. Conversion to a function type moves that check into `Conversions.Implicit` as `ConversionKind.ToFunction` (added in T2) over a `BoundMethodGroup { Receiver: null, Function: { Kind: Function, !IsGeneric } }` (particles are part of the name, not of the type, so a function with particle-labelled parameters qualifies; round 3 §15), producing `BoundFunctionRef(Function, FunctionType)`; the emitter wraps the function in a per-function thunk with the `void* env` first parameter. `Panic.onPanic` keeps its path untouched (Q345).

**Calls through a value are `BoundCall`s of a synthesized invoke symbol.** Per `FunctionType` the compilation holds one `FunctionSymbol { Kind: FunctionKind.Invoke, Parameters: unnamed, ReturnType, ErrorSets, Fails }`; `BindCall` (`BinderCalls.cs`) adds a case for a callee whose type is a `FunctionType` and goes through `BindFunctionCall` with the value as `Receiver`. Everything downstream that keys on `BoundCall` keeps working: the `fails` check and `try` insertion (`ReportUnhandled`, BYN2602), `ErrorFlow`, the try/catch lowering, and `BoundTree.Children`. Two places must learn that a receiver without `HasThis` is the callee value: `Lowerer.CallParts` (drops the receiver unless `HasThis`) and `CEmitter.Call`. Round-3 step 5.3e's particle matching (`Particles.cs`) sees an invoke symbol's parameters as unlabeled and unnamed, so a labelled argument falls into the existing missing-parameter path.

**`it` is a binder decision, not a parser one.** The parser never sees `it` as a lambda; `BindArgumentValue` (`BinderCalls.cs`) checks, when the parameter type is a one-parameter `FunctionType` and the argument is not a `LambdaExpr`, whether the argument's syntax mentions the name `it` outside a nested `LambdaExpr`, and if so binds it as a lambda whose one parameter is named `it`. A depth counter makes a second such argument inside the first BYN2029; the counter starts at one inside a `requires` rule (round 3 §11, bound by step 5.3b), where `it` already names the checked value (Q361). `.name` with an expected function type is caught in `BindTargetMember` (`BindCall` passes `expected`) and reported as BYN2823.

**Effects ride on the type; checking goes in the effect pass.** `FunctionType.Uses` is resolved from a `UsesClause` as declarations' `uses` are, compared in identity (R3) and shown in `DisplayName`. Function-typed parameters are effect-polymorphic (round 3 §13: a function taking a closure inherits its effects): a call through a parameter charges nothing to its function, and a call that passes a `BoundFunctionRef` or `BoundLambda` to a function-typed parameter charges that argument's effects to the caller (a forwarded parameter charges nothing). Elsewhere (a local, Q359) the conversion checks the effects against the type's `uses` bound (BYN6005) and a call through the value charges that `uses`. All of it hooks into `EffectAnalysis.cs` (round-3 step 5.3d) in T5.

**Depends on dev at 58cfad9 (round 3 and spec 006 merged).** 007's grammar extends round 3's (semicolon-free termination, `let`/`var` local bindings, type-first declarations (J54), the `->` token, `uses`, particles); 007 adds cases and members, never reorders round-3 or 006 code. 006's cases in the switches both specs extend (`Conversions.Implicit`'s `ToDynRef`, `TypeParameterType.Occurs`, `Unify`, `CEmitter.CType`/`Key`/`Conversion`) stay in place; 007's go last in each switch.

## Risks & mitigations

- **Two-pass binding of bodies** (`Compilation.BindFunction`): the first `BindBody` lifts lambdas into `AllFunctions` and the second lifts them again. Mitigation: record lambdas lifted during a pass in the same `pass` tuple as instances and remove them where `pass.Instances` are removed; a golden with a lambda inside a function that has an untyped-literal `var` (the rollback trigger, `run/generics-var-literal-rollback.byn`'s shape) proves it.
- **`=>` after a type**: `=>` after a type is a function type's input form in some positions and an expression body in others (`bool isBig(i32 x) => x > 2`, `bool isEmpty => lines.isEmpty`). Mitigation: `ParseType` takes a flag from its caller saying whether a body may follow; return types and field types (which precede the name, so `=>` follows the parameter list or field name) pass it and never see BYN1055; parse goldens for both, recorded as Q352.
- **Statement-start speculation**: locals start with `let`/`var` and the C#-style `T name =` shape is only scanned to report BYN1043. `(a, b) => …` at statement start must not scan as a tuple type followed by a name. Mitigation: `ScanType`'s paren path returns -1 when the closing `)` is followed by `=>` and the elements are bare names; parse goldens for both statement shapes.
- **`fails`/`uses` lists inside a function type** (`(() -> Token fails A, B) next`): a function-typed parameter is parenthesized (J54), so in a parameter list the list ends at the closing `)`. In a type argument, a tuple element or a function type's own parameter list, `, B` stays ambiguous. Mitigation: there, the list takes one name unless parenthesised (`fails (A, B)`); recorded as Q352.
- **Tuple of one capture**: `TupleType` with a single field is never produced by the parser; the symbol and emitter accept any count, but `Key` "tup1_x" and equality helpers were never exercised. Mitigation: T7 adds a run golden with exactly one capture; if anything balks, the environment pads with a `bool`.
- **Environment temp per evaluation**: a lambda created in a loop reuses one temp, so a lambda value from iteration *i* held past iteration *i+1* would see new captures. Region analysis forbids that only if the lambda value borrows the temp. Mitigation: the lowered `LFunctionValue` reads the env temp as a `BoundLocal`, and `FunctionType.IsBorrow` plus the loop-scope region rules make a function value that escapes its iteration BYN3002; L014's table includes this shape.
- **Capturing a narrowed value** (`BindName` wraps a non-null `let` in a `Narrow` conversion; round-3 5.3c added state refinements `T is .s`): the capture must copy the narrowed value, not the optional, and keep a state refinement. Mitigation: captures record the `BoundLocal` read exactly as `BindName` produced it; the tuple field has the narrowed type.
- **Effects lowering**: settled. `provide` sets a context slot for its body (`Lowerer.Provide`), so a call through a `uses` function value passes nothing extra; T7 still makes the `fn` pointer's signature come from the same `Signature` path as named functions, with a run golden of a `uses` function type under a `provide` (Q362).
- **`-Wall -Werror` on pre-existing emission**: 006 T11 cleaned pre-existing emission; 007 fixes only new warnings from lambda emission and records any narrowing in its proof notes.
- **`it` detection by syntax walk** runs on every argument to a function-typed parameter; it is linear in the argument's size and only when the parameter type is a one-parameter function type, so no measurable cost. A `NameExpr` named `it` that resolves to a user local named `it` is still rewritten; Q348 records that a local named `it` cannot be passed bare to such a parameter (write a lambda with a named parameter instead).
- **Lambdas inside generic templates** are bound once on the template (ownership runs there) and once per instance (flow, regions); the lifted symbol must exist per instance with substituted types. Mitigation: the lambda is lifted during the binding that creates it, so each instance's `BindBody` creates its own; `FunctionName` adds the instance's `TypeArgs`.
- **Goldens of `.ast` dumps**: new node kinds change no existing dump; `parse/` additions only.

## Self-hosting gaps

What spec 009's port must work around, given this subset:
- No stored callbacks: a visitor table, a `Dictionary<TokenKind, Func<…>>` or a parser rule table becomes a `switch` or a function-typed parameter threaded through the calls.
- No function-typed fields or return types: a "parse this then that" combinator style is out; helpers take their callback as a parameter each call.
- No `ref` captures: a lambda that must update a counter takes it as a `ref` parameter of the called function instead, or the loop is written out.
- No built-in `where`/`select`/`sort(by:)`: the port writes `any`, `indexWhere` and a `sort(by:)` over spans once in its own prelude.
- No generic aliases: `type Predicate<T>` is spelled per type (`type TokenPred = Token -> bool`).
- No effect variables: a function-typed local that may use an effect declares it in its type (`let hook: string -> string uses fs = …`); parameters need nothing (they inherit their argument's effects).
- No lambdas in `const` initializers and no function values in `static` data: keyword tables stay arrays of names, not of handlers.
- No `this` capture: a method that passes a lambda copies the fields it needs into `let` values first.
