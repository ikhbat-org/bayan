## 0. Ground rules (read first)

1. **Additive and opt-in.** Every new behaviour sits behind a new flag, subcommand or environment variable. When none of them is used, `bayan build`, `run`, `test` and `new` must give byte-identical output, emitted C and binaries compared with `dev`. Check this before every merge.
2. **No syntax.** No keyword, operator, clause, attribute or grammar form. This holds whether or not the rev 0023 syntax freeze has lifted.
3. **No spec or diagnostic edits.** Do not edit SPEC, GRAMMAR, DIAGNOSTICS, STATUS, `DiagnosticCodes.cs` or the goldens under `tests/cases/`. Any user-visible change also needs a **draft** revision in `docs/revisions/`, marked `Status: draft`. Do not apply it. §4 lists them.
4. **Own directories.**
   - `docs/tooling.md`: inventory, how to run each feature, and a status table.
   - `scripts/tooling/`: runners and measurement scripts.
   - `tests/tooling/`: tests for the new tools (MCP transcripts, watch tests).
   - `bench/soa/`: the SoA benchmark.
   - `csharp/Bayan.Mcp/`, or a self-hosted module if T0 says that's the shipped driver: the MCP server.
5. **Two touch points in in-flight code, no more:**
   - registering the `mcp` subcommand and the `--watch` flag in the CLI's command dispatch,
   - the debug-only allocation hook in the runtime C (T4).

   Each one:
   - is the smallest possible change,
   - goes in its own commit,
   - is rebased on `dev` and lands **between** milestone waves,
   - never edits a file the current wave is changing. If that's unavoidable, wait for the next gap.
6. **Not a blocker.**
   - New CI jobs are report-only (`continue-on-error` or the equivalent).
   - The existing CI must not get slower.
   - If a step fails or conflicts with milestone work, stop that step and record it in `docs/tooling.md`. Don't work around it in milestone files.
7. **Tooling language.**
   - Use POSIX shell or Bayān.
   - Use C# only inside the existing CLI projects: NativeAOT-compatible, with `System.Text.Json` source generation and no reflection.
   - No Python, Node or Deno, and no new NuGet dependencies.
8. **Share the inventory.** If the hardening H0 inventory exists in `docs/hardening.md`, use it and record only the extra facts below.

## 1. Phases

### T0. Inventory (read-only)
Record in `docs/tooling.md`:
- **Shipped driver.** Which driver is the shipped `bayan`: the C# CLI or the self-hosted driver? Where is command dispatch, and how are flags parsed?
- **Existing agent guide.** Does the repo already have an agent guide (`CLAUDE.md`, `AGENTS.md`, `HANDOFF.md`)? What does each say?
- **Rebuild cost.** Is incremental rebuild built, and how fast is it on the self-hosted source and on one `run/` golden? SPEC §21.3 targets under 100 ms.
- **Allocator.** How is the `General` allocator implemented in the runtime C? Is there a debug-only code path, and what macro guards it?
- **JSON output.** Is `bayan test --json` built? Is `--diagnostics json` built on all four commands (`check`, `build`, `run`, `test`)?
- **Lists.** Is `List<T>` built, and how is it laid out in emitted C?
- **Lints.** Do any existing lints match V 0.5.2's?
  - unused private functions and constants,
  - self-comparison (`x == x`),
  - a local that shadows a function,
  - large implicit struct copies.

  Search DIAGNOSTICS and the binder, and list matches by code.
- **Phase timing.** Does the compiler report time per phase (a `--timings` flag or similar)?

### T1. Repo agent guide (docs only)

### T2. `bayan run --watch`
- Add a new flag, `bayan run --watch [path]`. It does a normal `bayan run`, then watches the package's `.byn` files and `package.byn`. On any change it:
  1. debounces for 100 ms,
  2. stops the running program (SIGTERM, then SIGKILL after 2 s),
  3. rebuilds,
  4. restarts.

  It prints one status line per cycle: `rebuilt in 84 ms` or the diagnostics count.
- **Debug mode only.** `--watch` with `--mode` other than `debug` is a usage error (exit 2).
- **Watch by polling modification times.** Use a 200 ms interval. Polling avoids per-OS file-watch APIs and new dependencies.
- **On a compile error:** print the diagnostics, keep the old program stopped, and wait for the next change. Never exit on a compile error.
- **Ctrl-C** stops both the watcher and the program, and exits with 0.
- `--help` marks the flag `(experimental)`.
- **Tests** go in `tests/tooling/watch/`. A shell script starts watch on a temp package, edits a file and asserts the program's new output. It also covers a broken edit followed by a fixed edit.
- **Scope:** only the shipped driver. If the other driver lacks the flag, note it in `docs/tooling.md`.
- Hot swapping inside a running process (`@live`) is out of scope (§4, V3).

### T3. Allocation report (debug runtime only)
- When `BAYAN_ALLOC_REPORT=<file>` is set and the binary is a debug build, the `General` allocator records, per call site, the number of allocations, total bytes and peak live bytes. It writes the table to `<file>` at exit.
- **Call sites** come from `__builtin_return_address(0)` inside the debug allocator path. Don't change codegen to pass locations.
- `scripts/tooling/alloc-report.sh <binary> <report>` turns the addresses into `.byn` file:line using `addr2line` or `llvm-symbolizer`, which resolve through `#line`. It prints the table sorted by bytes.
- **Release builds:** in `safe`, `fast` and `small`, the code is compiled out by the existing debug guard. Check with the byte-identical test from §0.1 that the emitted C and binaries for those modes don't change.
- **Debug builds without the variable:** only the cost of one branch, and none if T0 finds an existing debug hook to reuse.
- **Tests** go in `tests/tooling/alloc/`. A program with known allocations must produce known counts and resolved lines.

### T4. `bayan mcp` (stdio MCP server)
- Add a new subcommand, `bayan mcp`. It speaks MCP JSON-RPC over stdio (`initialize`, `tools/list`, `tools/call`). Pin the current stable MCP protocol revision and record it in `docs/tooling.md`.
- **Thin wrapper.** Each tool runs the `bayan` binary itself as a child process with the right flags, and returns its stdout, stderr (the `--diagnostics json` lines) and exit code **unchanged** in the tool result. It never links compiler internals. That keeps it out of in-flight code and means its output always matches the CLI.
- **Read-only tools:**

  | MCP tool | Runs |
  |---|---|
  | `bayan_check` | `check --diagnostics json` |
  | `bayan_test` | `test --json --diagnostics json` |
  | `bayan_format_check` | `format --check` |
  | `bayan_explain` | `explain CODE` |
  | `bayan_audit` | `audit` |

- **Writing tools.** `bayan_build`, `bayan_format` and `bayan_fix` exist only when the server starts with `--allow-write`.
- **Inputs.** Each tool takes a `path`, which must resolve inside the server's working directory. Any other path is a tool error.
- Each tool has a one-line `description` that names the exit codes from SPEC §21.2.
- **Tests** go in `tests/tooling/mcp/`: recorded JSON-RPC transcripts (request in, expected response out) run by a shell script. Normalize absolute paths in the comparison.
- `--help` marks the subcommand `(experimental)`.

### T5. SoA measurement (no compiler change)
- In `bench/soa/`, write two Bayān programs doing the same particle update over 1M, 10M and 50M elements:
  - `aos.byn`: `List<Particle>`, where `Particle` has `f32 x, y, vx, vy`,
  - `soa.byn`: a hand-split `struct Particles { List<f32> x; … }`, with one list per field.

  Each program prints a checksum, and the two checksums must match.
- Add a third case that reads whole elements, so the gather cost shows.
- `scripts/tooling/soa-bench.sh` builds both in `fast` mode with clang and gcc, runs each 10 times, and reports the median time and peak RSS.
- Put the numbers in the draft revision V1. If SoA isn't at least 1.5× faster on the update loop, V1 should say so and recommend dropping the idea.

### T6. Compiler memory (report-only)
- `scripts/tooling/compiler-rss.sh` reports peak RSS (`/usr/bin/time -v`) for:
  - a cold self-hosted build by each bootstrap stage,
  - `bayan check` on the self-hosted source.
- If T0 found per-phase timings, it also reports RSS per phase. Don't add a compiler hook to get it.
- Wire it as a weekly, report-only CI job. If `claude/BAYAN-HARDENING.md` H10 is already built, add it there instead of creating a second job.

## 4. Draft revisions (write as `Status: draft`; do not apply)

**V0 — tooling surface.** SPEC §21.2 rows for:
- `run --watch`,
- `bayan mcp` (and its `--allow-write`),
- `BAYAN_ALLOC_REPORT`.

This also needs STATUS rows. Include T2–T4's measured behaviour.

**V1 — `@soa`.** A compiler-built attribute, applied like the existing `@` attributes, so the grammar doesn't change.

```csharp
@soa
struct Particle {
    f32 x
    f32 y
    f32 vx
    f32 vy
}
// List<Particle> stores one column per field; ps[i].x lowers to ps.x[i]
```

Rules to decide:
- rejected on structs with `requires`, `states` or `unique` fields,
- `let p = ps[i]` gathers a copy,
- `ref ps[i]` is rejected in 0.x,
- a new diagnostic code.

Attach T5's numbers. Build it only after the freeze lifts and the current codegen milestone lands.

**V2 — `bayan new` writes `AGENTS.md`.** Use a template based on T1. It changes `bayan new`'s output, so it needs a revision.

**V3 — `@live` hot reload.**
- Only function bodies are reloadable, and only in debug builds.
- A signature or type change restarts the program.
- `@live` functions have no static state.
- `@live` in a release build is an error.

Leave it in Appendix B until Loom needs it and T2 has proved out.

**V4 — lints.** Only the ones T0 found missing:
- unused private function or constant,
- self-comparison,
- a local that shadows a function,
- a large implicit copy, with the threshold set in `style`.

Each needs a code and a default severity, `.suggestion` per §19.2.

**V5 — toolchain pin.** A `toolchain: "0.3.x"` key in `package.byn`, checked by `bayan doctor`.

**V6 — `bayan pkg why <dep>`.** Once dependencies are built.

**V7 — `bayan translate header.h` and `comptime CImport`.** Once FFI (SPEC §18) is built. Output goes to a readable `extern c { … }` file in `gen/`.
