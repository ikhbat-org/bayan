# BYN2762: a `Map` cannot be copied

**No longer reported.** Retired in spec 002: replaced by BYN2780. Every collection, `StrBuf`, `Owned` and `unique struct` is now unique, and any implicit copy of one is BYN2780, with `move` or `.copy(to: alloc)` as the fix. The code stays reserved.

**Why (before spec 002).** A `Map` (and a growable `StrBuf`) is a small header over storage on the heap. Copying the header would leave two values sharing that storage: a `set` through one can rehash, free the old arrays and leave the other pointing at freed memory. Until maps can be copied safely, storing an existing map anywhere else is rejected: in a `let` or `var`, an assignment, a struct, union or tuple, an array literal, a `for` loop variable declared with `var` (each iteration copies the element; `let` loop variables are immutable, so they are fine), a `with` that leaves a map field in place (a field it replaces is not copied), `List.add` or `Map.set`, or a `return` of anything but a local that is going out of scope. The same holds for a value that contains a map by value, through struct fields, union payloads, tuples, arrays, optionals or `Result`s. Reading the map in place is fine: calling its members, looping over it with `for`, formatting it, or passing it as an argument (read-only or by `ref`). A fresh map, from `Map<K, V>()` or any call, can be stored anywhere.

**Example.**

```
var a = Map<i64, i64>()
a.set(1, 10)
var b = a
b.set(2, 20)
```

**Fix.** Keep one map and pass it by `ref` where it is changed:

```
void addTwenty(ref Map<i64, i64> m) {
    m.set(2, 20)
}

var a = Map<i64, i64>()
a.set(1, 10)
addTwenty(ref a)
```

or build a new map and copy the entries into it with a `for` loop.
