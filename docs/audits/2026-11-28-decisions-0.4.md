## 2. Decisions

### 2.1 Cancel handle created inside a child task

A `CancelSource` made inside a child task points into that task's memory region, so when the child ends, the handle points at nothing:

```bayan
let t = spawn makeSource()   // the child makes the cancel handle
let src = t.join()           // the child has ended; its memory is gone
scope(cancel: src) { … }     // under (b), src points at freed memory
```

- **(a)** The handle has one owner, and a second holder calls `src.share()`, the same verb channels use. Safe everywhere. It changes the one line in the concurrency doc that says copies share the handle.
- **(b)** Keep free copying; a child that hands one out keeps its memory region alive past its end.
- **Recommended: (a).**
- **Spec check:** (b) is not the current rule. §9.4 rule 3 makes storing a borrow anywhere that outlives its region a compile error, and BYN3217 (reserved) covers a reference crossing into a fiber. (b) would add a new exception to region checking, not keep existing behaviour.
- **Work:** apply (a) in the concurrency doc. `CancelSource` follows §3.11: anything holding the handle is `unique`, so moving it needs `move` and a second holder needs `share()`.
- **Tests:** a must-reject golden for an implicit copy (BYN2780), and a run golden that shares the handle and cancels from both holders.

### 2.2 Reading process output in chunks

The two options as proposed:

```bayan
while let chunk = try output.read(max: 65536) { … }   // (b): chunk is Untrusted<List<u8>>
let n = try Io.stdin.read(to: buf.span)               // (a): fills your buffer, plain bytes
```

- **(a)** Fill the caller's buffer: no allocation per chunk, but it loses the `Untrusted` mark.
- **(b)** A new list per read: keeps `Untrusted`, at one allocation per chunk.
- **Recommended: (c).** Fill the caller's buffer and return a view of only the bytes just written:

  ```bayan
  var buf = List<u8>(capacity: 65536)
  while let chunk = try output.read(to: buf.mutableSpan()) { … }   // chunk: Untrusted<ReadOnlySpan<u8>>
  ```

  It allocates nothing and keeps the mark. The view borrows `buf` (§9.4 rule 4), so the next read, which writes `buf`, can't run while `chunk` is alive (rule 5). A read-only view copies freely (§3.11).
- **Spec checks:**
  - The particle is `to:`. `into` is not a particle (§10), so `read(into: …)` would be BYN5008. `max:` is fine only as an optional named parameter; as a required parameter it needs a particle (BYN5006).
  - `i64 Io.stdin.read(to: Span<u8> buffer)` already exists in §15.1 and returns a count. (c) either becomes the shape of the new process-output stream, or changes `stdin.read` by revision. Don't give one name two return types.
  - §15.1 still says `readAll` returns a plain `string`, and that sources are not yet wrapped. The 11-27 decision to return `Untrusted` needs a revision before (b) or (c) can depend on it (§3.3).
  - The memory risk of (b) is under the wrong allocator. A `List` chunk is `unique` and is freed when each iteration ends under `General`, `main`'s allocator (§9.2). It only grows under the never-freed arena that scripts use by default.
- **Work:** if (b) is chosen instead of (c), add a script golden (an arena allocator, not `main`) that reads a large stream in a loop and asserts that peak memory stays bounded.

### 2.3 Units whose sizes don't divide each other

```bayan
unit Base(b): i64
unit Two(tw) = 2 b
unit Three(th) = 3 b
let x = 1tw + 1th        // (a): error BYN2208, convert to Base first
let y: Base = 1tw + 1b   // fine under every option
```

- **(a)** Mixing them is an error; this can be loosened later without breaking code.
- **(b)** Mix them in the base unit automatically.
- **(c)** Forbid such unit pairs where they are declared.
- **Recommended: (a).**
- **Spec check:** §3.4 already gives (a). Mismatched units are errors, and the only implicit conversion is to a finer unit; neither `Two` nor `Three` is finer than the other. This adds no new rule, only BYN2208 for this case.
- **Work:** when units are built, BYN2208's help names the common unit: "convert both to `Base`: `Base(x) + Base(y)`".
- **Side issue:** the symbol `b` makes `0b` ambiguous between zero `Base` and the binary prefix (`0b1010`). Unit suffixes are not allowed on hex or binary literals (§2.3), but the lexer still has to choose. Pick another symbol in examples, or settle that the `0b` prefix always wins and reject `b` as a unit symbol.

### 2.4 Process timeout precision

`timeout: 500us` waits 1 ms either way, rounded up so it never fires early. The only question is where the rounding happens.

- **(a)** The compiler rounds up, and the runtime stays in ms.
- **(b)** The runtime takes ns, which means changing three platforms and three runtime copies.
- **Recommended: (a).**
- **Work:**
  - Round wherever a duration converts to milliseconds, not only on literals: a duration computed at runtime (`timeout: d / 3`) needs the same round-up. That is `d.ceiling<Milliseconds>()` (§3.4), emitted by the compiler or a small helper, with no change to the runtime interface.
  - `IoError.timeout(Millis after, …)` reports the limit. With `500us` it reports `1 ms`, so record that in §15.1.
  - §16.5 renames `Millis` to `Milliseconds`; rename the payload type with it.
- **Tests:** a literal and a computed duration under 1 ms both produce a 1 ms timeout, and the payload reports 1 ms.
- **Note:** unit suffixes such as `500us` don't compile in 0.4 (STATUS: units spec-only). Until they do, this applies to whatever duration form the timeout accepts today.

### 2.8 Passing a temporary as a writable `Span` (already merged)

```bayan
void fill(Span<i64> s) { s[0] = 9 }
fill(make())     // now error BYN2106; this used to compile
```

- **(a)** Keep rejecting: one rule, which can be loosened later without breaking code.
- **(b)** Allow temporaries: harmless, but the writes are lost and are usually a bug.
- **Recommended: (a), limited to true temporaries.**
- **Spec check:** the second example from the original proposal, `fill(m["a"])`, conflicts with §10. Element access on a `var` `List` or `Map` yields the stored value in place, with no silent copy, so on a `var` map the write isn't lost, and `m["a"][0] = 9` is valid. Choose one:
  - **Narrow BYN2106** to temporaries (call results, literals) and to elements of a `let` collection, which are already BYN2104. **Recommended.**
  - Or amend §10 by revision so element access never gives a writable place. That breaks more code and contradicts §10's in-place example (`stats.getOrAdd("api").record(12ms)`).
- **Work:**
  - Passing a temporary as a `ReadOnlySpan<T>` must keep compiling; only writable spans are rejected.
  - BYN2106's help offers the fix: "bind it first: `var tmp = make()` then `fill(tmp)`".
  - The merge changed behaviour, so add the STATUS row and update `docs/diagnostics/BYN2106.md` in a follow-up commit.
- **Tests:** a temporary passed as a writable span is rejected; a temporary passed as a `ReadOnlySpan` compiles; an element of a `var` map passed as a writable span compiles and the write is visible afterwards; an element of a `let` map is BYN2104.
